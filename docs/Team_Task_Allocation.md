### 1.2 为什么这样分

**① 按"文件所有权"分，不按"界面区域"分。**
每人独占自己那几个文件，日常开发几乎不会同时改同一个文件，合并冲突自然就少。唯一的共享点是 `src/ui/app.py`——它由成员C 主写，其他人只在末尾追加自己的 `pack()` 调用，并且**冲突演练就安排在这里**（见 4.3）。

**② 五个角色刚好覆盖作业的四个评分维度。**

| 评分维度（占比） | 直接责任人 | 支撑责任人 |
| :--- | :--- | :--- |
| 文档规范 20% | 成员E | 马子尊（README）、全员供稿 |
| 协作流程 30% | 马子尊 | 全员（各自分支与提交） |
| Vibe Coding 25% | 成员E 汇总 | 全员各交 3 条提示词记录 |
| 程序实现 25% | 成员B | 成员C / 成员D |

**③ 示例工程 6 人，我们 5 人，砍掉的是"专职展示负责人"。**
示例里"课堂展示负责人"和"QA"是两个人；我们合并为成员E 一人（文档 + 测试 + 展示），因为本项目的展示材料（PPT、演示视频）与文档素材高度复用——同一张架构图既进设计文档也进 PPT。代价是成员E 工作量偏大，所以把 README 与答辩主讲交给马子尊分担。

**④ 每人都有一个"可以独立演示"的产物。**
这就是防"关键人物请假全组停摆"的办法：算法员交 `pytest` 全绿截图，界面员交可点开的空壳，渲染员交静态 mock，文档员交过审文档。任何一个人这周没来，其余四人仍能推进。

### 2.2 成员B　核心算法工程师

| 项 | 内容 |
| :--- | :--- |
| 定位 | 全组唯一"算错就全错"的位置，优先级最高 |
| 分支 | `feature/core-logic` |
| 依赖 | 无外部依赖（纯标准库）；被成员C/D/E 依赖 |

**任务清单**

- [ ] `bits.py`：位宽常量、`int → list[int]`、`list[int] → int`、符号位判定、补位/截断
- [ ] `represent.py`：原码 / 反码 / 补码 / 移码互转，处理 `−0` 与 `−128` 两个特例
- [ ] `negate.py`：`negate(bits)` 返回结果 + 进位链 + 逐步 trace（供动画用）
- [ ] `adders.py`：`add(a, b)` 返回 `list[BitColumn]` 与最终进位 `C_n`
- [ ] `overflow.py`：三种判定方法，返回带一致性的 `OverflowReport`
- [ ] 编写"算法推导笔记"（`docs/algorithm_notes.md`），把公式与教材页码对应起来
- [ ] 与成员E 一起把 14 条用例矩阵转成 `pytest` 断言
- [ ] 随机对拍脚本：200 组随机 `(X, Y, op)` 与 Python 原生整数结果比对

**必须处理的四个坑**

1. `−2^(n−1)`（`1000…0`）**没有相反数**，求补后仍是自己，必须报"超出范围"而非静默返回；
2. `−128` **没有原码 / 反码**表示，四码表对应位置要显示"不可表示"；
3. `0` 的原码有 `+0/0000 0000` 与 `−0/1000 0000` 两种，补码唯一；
4. 减法要先转成 `[X]补 + [−Y]补`，`[−Y]补` 的符号位也参与取反加一，不能只对数值位取反。

**验收标准**

- `pytest tests/ -v` 全绿，核心层覆盖率 ≥ 90%；
- 用例矩阵 14 条全部通过；
- 随机对拍 200 组零差异；
- `grep -r "tkinter" src/core/` 无结果（证明零 UI 依赖）。

## 四、协作机制

### 4.1 结对备份

| 结对 | 理由 | 备份内容 |
| :--- | :--- | :--- |
| 成员B ↔ 成员D | 算法输出直接喂给渲染，字段理解必须一致 | 互相能讲清 `BitColumn` 每个字段 |

| 马子尊 ↔ 全员 | 集成时任何模块都可能需要小修 | 掌握每个模块的启动方式 |

**交接标准**：接手者能在 **1 小时内**让程序跑起来并定位到出问题的函数，才算备份有效。

### 4.2 每日同步（群消息模板）


只写三行，不写长文。卡点超过一天必须升级给负责人。

### 4.3 冲突演练脚本（作业硬性要求）

**目标**：在 `src/ui/app.py` 的 `_init_window()` 上制造一次真实冲突，并留下记录。

```bash
# 1) 两人各自基于最新 main 开分支
git switch main && git pull
git switch -c feature/ui-layout      # 成员C
git switch -c feature/canvas-render  # 成员D

# 2) 成员C：把窗口尺寸改为 1280x800
#    self.root.geometry("1250x760")  ->  ("1280x800")

# 3) 成员D：同一函数里新增画布尺寸参数
#    self.root.geometry("1250x760")
#    self.canvas_w, self.canvas_h = 700, 420

# 4) 成员C 先合并（PR #1 已合入 main）
# 5) 成员D 拉取最新 main，触发冲突
git fetch origin && git merge origin/main
#    Auto-merging src/ui/app.py
#    CONFLICT (content): Merge conflict in src/ui/app.py

# 6) 在 VS Code 中打开，看到
#    <<<<<<< HEAD
#        self.root.geometry("1280x800")
#    =======
#        self.root.geometry("1250x760")
#        self.canvas_w, self.canvas_h = 700, 420
#    >>>>>>> origin/main

# 7) 协商结果：保留新尺寸 + 新参数
#        self.root.geometry("1280x800")
#        self.canvas_w, self.canvas_h = 700, 420

# 8) 标记已解决并提交
git add src/ui/app.py
git commit -m "fix(ui): 解决 main 与 feature/canvas-render 在窗口初始化参数上的冲突"
git push
```

**留档要求**：冲突界面截图 1 张 + 解决后 `git log --graph --oneline` 截图 1 张，存入 `docs/images/`。

### 4.4 合并窗口

- 每周五 20:00–21:00 为合并窗口，负责人在线处理 PR；
- 非窗口期也可以合，但**必须提前在群里说一声**，避免两人同时改 `main`；
- 合并前自查：`pytest` 通过、无 `print()` 调试残留、无注释掉的大段代码。
